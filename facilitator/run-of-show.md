# McNeese AI Harnesses: two-hour run of show

Audience: faculty and staff beginners. Delivery: mental model, GitHub primer, Field Guide example, short end-to-end demos, and audience-led practice. Primary outcome: participants can explain what a repository and harness are, describe a workflow they want AI to help with, and decide whether an AI-produced result is good enough to use.

| Minute | Segment | Observable check |
| --- | --- | --- |
| 0-15 | Introduce the mental model: model versus harness, project context, permissions, and the human review loop. Invite participants to hold onto a question or workflow they wish AI could help with. | Participants can say what the harness may inspect or change and what remains their decision. |
| 15-35 | Explain Git versus GitHub, repositories, commits, and public versus private visibility. Show a small repository and its change history. | Participants can identify where project files live, what changed, and what remains private. |
| 35-70 | Build the idea of a harness around a sample workflow: a project folder, standing brief, allowed inputs, tools, output location, and success checks. Use the Almanac Field Guide to show how the same pattern scales to durable files, optional capabilities, GitHub backup, and review rules. | Participants can outline the pieces of a harness for their own work without installing one. |
| 70-95 | Run two quick, prepared end-to-end examples. For each: start with a question, inspect relevant context, make one bounded change or draft, and verify the output. Show a before/after or diff and reject a weak suggestion. | Audience sees a complete, checked workflow rather than a polished answer alone. |
| 95-120 | Open questions and interactive audience examples. Ask for a question or workflow, choose a safe public or synthetic stand-in when real materials are private, then try a few live. Close with the setup paths and one next task. | Participants leave with a use case and a way to judge whether its result is trustworthy. |

## Demo preparation

Use a synthetic, non-sensitive repository for the prepared examples and live audience requests. Keep a known-good copy and a pre-recorded fallback. Before the session, test the exact tasks in both tools, GitHub access, network access, screen readability, and a clean reset. Keep the practice repository private unless its contents are intentionally public. Never screen-share a personal vault, student files, emails, or live credentials. If a tool fails, narrate the same scope, inspect, act, verify loop using the prepared before/after files.

Prepare two short examples with different shapes, such as improving a one-page event checklist and checking a tiny synthetic CSV summary. Keep each example small enough to complete and verify in roughly 12 minutes. Audience requests may be broader questions or recurring workflows; translate them to safe, bounded demonstrations rather than opening private data live.
