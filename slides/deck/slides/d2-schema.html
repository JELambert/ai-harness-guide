Step 2 · Inspect the design

Three tables, one key decision

Ask the harness to propose the schema and explain the key before it writes code.

Keeping every release, not only the latest, is what makes Demo 1’s drift a query instead of a surprise.

CREATE TABLE releases (

  version TEXT PRIMARY KEY,

  fetched_at TEXT, n_rows INT);

CREATE TABLE events (

  country TEXT, ccode INT,

  year INT, month INT, day INT,

  coup INT,  -- 1 failed, 2 success

  release TEXT REFERENCES releases);

CREATE TABLE papers (

  openalex_id TEXT PRIMARY KEY,

  ccode INT, title TEXT, year INT,

  doi TEXT, is_open_access INT);

The key decision is how to identify an event across releases. Country code plus full date is the obvious key, and Demo 1 just showed why it fails: a date correction looks like one deleted coup and one new coup. Let the harness propose a key, then ask what happens to Chad 2006. A good answer is to keep releases separate and match with a tolerance, flagging near-matches for a human.
