Make the work visible.

We will start with a familiar version-control mess, build a tiny AI harness around a real workflow, and inspect the result together. Guided demo, no installation required.

Part 1 / Mental model

A model is not a workflow.

A chat assistant answers what you paste. A project-aware tool can inspect files, propose edits, run checks, and see errors. That extra context removes many obvious mistakes. It does not decide whether the resulting claim, grade, or recommendation is right.

“AI drafts. You decide.”

That is the same division of labor in the AI crash course and in BUS 751. The assistant handles mechanical work; your subject knowledge defines the target and certifies the result.

What makes it a harness?

The model plus an environment

Context: files and source material it may read.
Instructions: the job, constraints, and output format.
Tools: the ability to edit, search, or run checks.
Boundaries: what needs review before it leaves the workspace.

A capable tool can make a subtle mistake that runs cleanly and looks polished. The more fluent the output, the more important the check.

Part 2 / About 20 minutes

Stop naming files “final_final.”

We begin GitHub with a problem everyone recognizes. A shared folder of agenda_final.docx, agenda_final_v2.docx, and agenda_USE_THIS.docx cannot tell you which is authoritative, what changed, who changed it, or why.

Git

The project remembers

A repository is a project folder with a history. A commit is a named checkpoint for the project, not another copy with “final” in its filename. A diff shows exactly what changed.

GitHub

The project has a shared home

GitHub stores a remote copy and gives collaborators a place to inspect files, changes, and history. Check whether a repository is public or private. A local commit is not on GitHub until it is pushed.

Live check: Open a sample repository. Find its README, one change in the history, the before/after diff, and the visibility setting. A useful README answers: what is this, why does it exist, and where should I look first?

Part 3 / Build a harness

Give the assistant a desk.

Our example is a small faculty workshop. The job is to improve a one-page participant guide using a source brief and an agenda. The assistant must not invent logistics, contact attendees, or publish. The point is not the product; it is the repeatable arrangement around it.

A deliberately small repository

workshop-guide/
├── README.md       what this project is
├── brief.md        dates, audience, constraints
├── agenda.md       current session plan
├── guide.md        participant-facing draft
└── AGENTS.md       standing work instructions

The standing brief

What AGENTS.md says

Read brief.md and agenda.md before touching the guide. Keep logistics grounded in those files. Save a draft in guide.md. Run a cross-check and show the diff. Do not send email or publish without a separate decision.

This is the portable pattern behind the Almanac Field Guide: durable files, explicit roles, optional capabilities, and review before outward action. We are borrowing the architecture, not asking anyone to build an Almanac.

Ask first: What would make this result wrong? If you cannot name a failure condition, neither you nor the tool has a clear target.

Part 4 / Two short demonstrations

From request to checked result.

We will compare the work, not just applaud the answer. The first demo revises the workshop guide. The second checks a small synthetic attendance table. Both finish with evidence and a keep/revise/reject decision.

  1. Describe intent“Make a one-page participant guide that matches the brief.” Name the source files, audience, desired length, and no-send boundary.
  2. Inspect before writingAsk what the assistant found, what it cannot confirm, and which files it plans to change.
  3. Draft one bounded changeLet it edit only guide.md. Review the diff in GitHub or the desktop app.
  4. Check the claimCompare dates and venue with brief.md. For the table, count rows and calculate one total by hand.
  5. Own the decisionKeep the accurate change, revise the weak one, or reject it. A finished draft is not a sent announcement.

Prompt 1 / Explain before write

Read README.md, brief.md, and agenda.md. Before editing, tell me who this guide is for, what facts the files establish, what is missing, and one way the draft could be wrong. Do not change or send anything yet.

Prompt 2 / Act and verify

Revise guide.md into a one-page participant guide using only the facts in brief.md and agenda.md. Do not invent dates, venues, or attendance; do not email or publish. Show the diff, check every logistical claim against its source, and list anything that still needs my decision.

Transfer this to data work: “Read the two tables, report the join key's type in each, preserve every order row, and show row counts before and after.” That comes from the BUS 751 method: specify the source, target, constraint, and falsifiable check.

After the workshop

Your first harness can be tiny.

Choose one repeatable task. Put its source files in a project folder, add a short standing brief, ask for one bounded change, and decide how you will check it. Add integrations only after that simple loop works.

A useful habit from BUS 751

Explain. Test. Compare.

Ask for an explanation before a rewrite. Ask for a check that fails on a bad result. Ask for alternatives and tradeoffs before making a consequential choice. These habits work with or without an AI tool.

Exit question: What did the assistant change, how did you verify it, and what decision remained yours?
